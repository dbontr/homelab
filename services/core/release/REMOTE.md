# Authenticated fleet release — source-level design

The deployment architecture separates three independent authorities:

1. The owner signs into the protected browser portal on the security host with password and TOTP. Its session remains revocable, with a 120-minute idle limit and a 12-hour absolute limit.
2. Each host executor has an operator-provisioned TLS server identity. Only a coordinator with a trusted client certificate and matching DNS SAN may call the typed executor API. The original signed owner assertion travels in an HTTP header, not an MCP tool argument.
3. Each remote executor asks the central `homelab-securityd` for **every** authorization decision using a separate mutually authenticated TLS connection. The central service verifies the signed owner identity, current session, operation, target and exact canonical arguments. Its remote listener exposes operation authorization and read-only replay policy checks on the mutually authenticated executor connection. Owner login, confirmation, revocation and plaintext vault administration remain on separate protected owner channels.

The NixOS modules leave both TCP endpoints **disabled by default**. The separate staging endpoint requires the exact `infrastructure__release_stage` policy and returns a host-bound manifest without activating it. Operators must explicitly provide private-IP listeners, TLS certificates, private keys, trust anchors, certificate DNS identities, permitted release operations and host-specific security policies using protected systemd credentials. No TLS secrets belong in Git or in MCP arguments. The executor still denies activation when `allowReleaseActivation = false`, even if a client presents a valid certificate.

## Fleet behavior

`release.RemoteReleaseAgent` implements `HostReleaseAgent` and `RequestIdentifiedReleaseAgent`, and observes the local release journal. `release.DurableFleet` journals a random transaction identity, ordered host targets, and each intent **before** sending a remote command. It derives a separate 128-bit request identity from the transaction, host, release and operation, and passes that same identity to the host executor for every corresponding attempt. Hosts without a request-identified execution interface are not eligible for a durable transaction. It writes owner-only records atomically and synchronizes the containing directory. Rollouts proceed compute-first and control-last, and successful hosts are rolled back in reverse order after failure.

The trusted `FleetOrchestrator` writes a private, immutable plan record after all host manifests have been validated. Activation accepts only the opaque plan identity and acquires the same fleet journal lock before loading the plan and writing activation intent. An owner or gateway cannot substitute arbitrary per-host release IDs at activation time. A fully resolved transaction and its plan can be cleared together; ambiguous outcomes cannot be cleared. 

A lost reply is **not proof of either success or failure**. The host binds each request identity to its exact authorized operation, target and canonical argument digest, durably writes the start event before executing, and returns a matching audit receipt. Retries with the same ID can recover a recorded result only after a fresh read-only owner-policy check; unresolved attempts never trigger another effect. Unknown host outcomes require signed, authorized journal observations with an exact matching release ID; the coordinator never blindly retries an ambiguous switch. Unresolved transactions remain in an attention-required state, and only completed or fully reverted transactions can be cleared.

## Fleet coordinator

`homelab-fleetd` owns the operator-provisioned TLS client certificate and durable fleet state. It runs under the separate `homelab-fleet` system user and exposes only a protected Unix socket to the platform gateway. The gateway forwards a signed owner assertion; it never holds the fleet TLS client key. Every operation is independently authorized by `homelab-securityd` against an exact `fleet` resource and operation. Host executors then separately authorize the exact host operation.

The opt-in `services.homelabFleet` NixOS module configures pinned HTTPS endpoints, expected server certificate identities, protected systemd credentials, and a compute-first/control-last list of at most 16 hosts. Configure `services.homelabPlatform.fleetSocket = "/run/homelab-fleetd/fleet.sock"` on the gateway host to enable MCP discovery of stage, plan, activate, status, recover, and clear tools. No live cluster change follows from adding source files alone.

The security policy must allow explicit `infrastructure__fleet_prepare`, `infrastructure__fleet_stage`, `infrastructure__fleet_plan`, `infrastructure__fleet_status`, `infrastructure__fleet_activate`, `infrastructure__fleet_recover`, and `infrastructure__fleet_clear` operations for target `fleet`. Recovery, activation, and clearance require separate owner step-up. Exact per-host `infrastructure__release_stage`, `infrastructure__release_status`, `infrastructure__release_activate`, and `infrastructure__release_revert` policies are still required on the independent security service.

The `infrastructure__fleet_prepare` tool performs a non-consuming authorization preflight across all configured host activation operations, and the fleet activation endpoint repeats that preflight before writing an activation transaction. A missing host confirmation produces a host-by-host `confirmation_id` report; it cannot begin a partial rollout merely because an approval was missing. The independent security service verifies owner identity, session, exact operation, target and canonical arguments for each preview. A preview never refreshes the session or consumes a confirmed challenge. Each host reauthorizes its operation at the instant of execution.

**The existing two-minute confirmation expiry still applies.** If an approval expires during a long rollout, later hosts can refuse activation; preflight does not solve the need for transaction-scoped batch approval or long-running release scheduling. Reverse rollback still requires independent authorization. Until those mechanisms are implemented, treat this orchestration as experimental and do not rely on it for unattended critical routing changes.

The owner must confirm destructive operations through the protected browser before retrying identical arguments. Multi-host preflight and transaction-scoped approvals remain necessary to avoid expiration of per-host single-use confirmations during long rollouts; the source does not claim unattended five-host deployment.

## Deliberate remaining limitations

These are building blocks, not an automatically deployable five-host system. Remote staging from a clean, trusted checkout with an exact Git commit is available through the protected host executor. Fleet stage plans validate every manifest against the host and revision. Each host must already have the matching Git source and offline Nix inputs; source provisioning and Nix store closure distribution are not implemented. Host credential provisioning, fleet-wide authorization preflight and owner confirmations, health checks beyond existing local service probes, router reachability watchdogs, and live multi-node verification remain outstanding. Security policies must include exact `infrastructure__release_status`, `infrastructure__release_activate` and `infrastructure__release_revert` target entries. No host is activated by importing this package or enabling the NixOS module source in a repository.

Tests exercise fake agents, transaction persistence, recovery, and in-process TLS clients. They do not establish successful NixOS switches or safe router failover. See root `REFERENCES.md` for standards.
