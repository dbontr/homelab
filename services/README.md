# Services

Services own application state, business decisions, authentication, scheduled work, hardware operations, and long-running tasks. They do not depend on a browser, an MCP connection, or a public API listener.

The primary application runtime is in `services/core/`. The private core router retains authentication and the canonical personal state store. Personal task, goal, rule and planning HTTP operations belong to `services/core/internal/personal/`; bounded monitoring and media HTTP adapters live in `services/core/internal/monitoring/` and `services/core/internal/mediahttp/`. Book request and discovery routes are owned by `services/core/internal/bookhttp/`, with revision-guarded records in the canonical personal store and an optional catalog. Prometheus, Loki and Seerr retain their own service lifecycles and data. Calendar is an independently enabled read-only Go process; it owns the protected external feed URL and shares only bounded event data with the authenticated platform client. Compute, Learning and Health are independent Go modules in `services/compute/`, `services/learning/` and `services/health/`, with their own state and failure boundaries. Moonfin/Seerr, monitoring collectors, SQL-backed applications, and K3s remain independently operated infrastructure components; an interface outage must not stop them.

`services/bridge/` contains the restricted internal HTTP transport used by the optional MCP and public API entry points. It does not own application records or privileged operations. The service runtime remains the only owner of its writable state. The core startup acquires exclusive file leases for personal tasks, recipes, profiles and workflow state before initializing those stores. Independent processes must exchange domain operations through authenticated interfaces rather than open the same records as additional writers.

The browser uses owner-session routes and CSRF checks. Neither the browser nor an interface gateway may receive a service's administrator credential. Public interfaces require separate client and route-scoped service credentials; disable or stop those processes without removing the underlying services.
