# Kubernetes batch admission

Kueue v0.20.6 provides admission and quota control for batch Jobs in the `pwm-batch` namespace. K3s owns the versioned Helm release through the `kueue` HelmChart resource in `kube-system`. The Saturn NixOS service reconciles the controller and queue resources after the Kubernetes API is ready.

The `research-cpu` LocalQueue maps to the `pwm-cpu` ClusterQueue. Its ResourceFlavors select physical Venus and Mercury using the standard Kubernetes hostname label, so batch Jobs do not land on Saturn. Conservative admission quotas limit Venus to 1 CPU and 2 GiB, and Mercury to 2 CPUs and 4 GiB. These limits bound Kueue admission, not total Kubernetes node usage; the scheduler still checks physical resource availability.

Queue management is opt-in. The manager handles `batch/job` only and sets `manageJobsWithoutQueueName: false`. Its managed namespace selector requires `homelab.dbontr.me/kueue: enabled`. Unlabeled system Jobs, existing controller Deployments, Compute Pods, and independent hardware leases remain outside Kueue admission. Do not enable Pod or Deployment integrations, or automatic admission for every namespace, without separate migration acceptance.

## Verification

Run `bash scripts/verify-kueue.sh --check` on Saturn for a read-only controller, queue and cluster audit. Run `bash scripts/verify-kueue.sh --smoke` for an isolated, resource-limited Kubernetes Job that checks Kueue admission and cleans up its test Job. Neither mode changes service configuration or controller-maintained Compute state.

New batch Jobs in `pwm-batch` must label their Job metadata with `kueue.x-k8s.io/queue-name: research-cpu` and declare CPU and memory requests. Follow the namespace's restricted Pod Security requirements. Do not apply Kueue labels to Compute-managed Pods or Jobs until both admission systems share a single tested resource-allocation contract.

## Maintenance

Keep the HelmChart manifest and the queue manifest in the homelab repository as the source of truth. Kueue's CRDs and admission webhooks are cluster-scoped; review chart upgrades, keep rollback receipts, and test existing workload creation before promoting new versions.

Do not uninstall the controller while Kueue resources remain. First finish or remove Kueue-managed Jobs, then Workloads, LocalQueues, ClusterQueues, ResourceFlavors and other Kueue resources, according to the official Kueue uninstall procedure. Removing the HelmChart does not justify deleting any Compute PVCs or media.

## Compute batch execution

The controller may enable `controller.kueue.enabled: true` in its Helm release after the Kueue queues and `pwm-batch-runner` service account exist. The controller receives a projected, audience-bound Kubernetes identity and namespace-scoped permissions for batch Jobs, Pod logs and Kueue Workloads. Interactive Workspace Pods and hardware leases remain under their original controller/worker paths. Kueue does not schedule hardware leases.

The public MCP uses `compute__submit_batch_job` and `compute__cancel_batch_job` for privileged CPU batch operations. These are typed requests to the independent Rust executor, not direct Compute backend forwarding. The executor checks the signed owner identity and active owner session, the exact project allowlist, an immutable image digest allowlist, CPU and memory bounds, and an audit-bound request ID before it can use its protected controller credential. The gateway derives the controller's idempotency key from the caller's 32-character execution `request_id`; a caller cannot supply a separate job key. A replay of the same identity cannot create a second batch job. The executor returns its durable audit `request_id`, while the controller owns a separate generated Kubernetes Job ID. Resolve the exact job using the owner-scoped read-only `compute__compute_job_by_request` tool with `project_id` and that same `request_id`; the response includes the controller Job ID, queue status and persisted result. Subsequent status checks use `compute__compute_job_status`, and project job history remains available through `compute__list_project_jobs`. Request lookup is project-isolated and does not grant execution permissions. This execution contract does not grant access to Kubernetes administrator credentials, interactive workers, or hardware leases.

Submit through `submit_compute_job` with `backend: kueue`, an immutable `image` reference ending in `@sha256:<64-hex>`, `request_id` (8–64 safe characters), `command`, `cpu` (0.1–2), and `memory_mb` (64–4096). Reusing a request ID with the same parameters returns the same persistent job. Inspect with `compute_job_status` or `list_project_jobs`; request cancellation with `compute_job_cancel`. Completion is recorded only after observing the Kubernetes Job terminal condition; cancellation is recorded only after confirming the Job is absent. Output includes up to 16 KiB of Pod logs, if available.

The controller stores pending Kueue jobs as `kueue_queued` internally, while presenting them as `queued` through MCP and REST. This prevents earlier Workspace controllers from claiming them during rollback, even if they lack the Kueue exclusion query. The controller's reconciler resumes pending submissions, observation, and cancellation after process restart. Before sending a Kubernetes Job creation request, the controller durably marks the outbound attempt in the same SQLite store that owns the job identity. If the response is lost, reconciliation searches for the exact existing Job and checks its immutable command, resources, project, request ID and UID. An absent Job after a recorded attempt enters `recovery_required` instead of being submitted again. This state also records successful execution whose Pod logs cannot yet be recovered. A later reconciliation may resolve the state when the original Job and its output become visible; an operator must investigate executions that remain absent. A cancellation request does not establish that an earlier uncertain execution never ran. Existing database rows without an attempt marker are conservatively fenced during schema migration. Jobs use restricted Pod Security, immutable images, no service account token, read-only root filesystems, CPU-only quotas, and a one-hour execution deadline. Project authorization is enforced before job submission and status access. Existing worker Jobs remain unchanged.

Deployment requires publishing an immutable controller image built from the accepted source and enabling `controller.kueue.enabled` in the controller Helm release. The live Kueue installation alone does not activate this Workspace feature.
