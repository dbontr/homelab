# Project Stewardship

A **Workspace project is not a Git repository**. Its stable project ID owns the relationship between independently governed source repositories, optional knowledge, shared libraries, a planning board, compute and artifacts. A repository can belong to more than one project. Do not derive the project's identity or knowledge destination from any one source repository.

## Procedure

1. **Identify the project.** Discover live Workspace MCP tools, authenticated principal, project IDs, grants, repository memberships, library links, knowledge policy, GitHub planning board and active resources. Select the existing project by its stable ID, not by a coincidentally named repository. An independent task needs no project. A project whose primary product is a reusable proof, code or research library uses the `library` project kind and publishes a library that other projects may link without inheriting its knowledge or repository permissions. Consult [project-model.md](references/project-model.md).
2. **Resolve source and linked resources.** A project can have zero repositories for non-code work or multiple source repositories with different roles and permissions. Link only explicitly selected repositories; verify provider identity, default ref and permission. For a library-focused project, use `create_library_project` to create the project and its own reusable publication atomically. Other projects use `library_link` to consume it. Keep the publisher and consumer distinct, with pinned Git sources and verified object hashes; never copy a library into project knowledge just to create an association.
3. **Select knowledge separately.** The default is `none`. When knowledge is authorized, prefer a **separate private GitHub repository named for the project**, such as `OWNER/PROJECT-SLUG-knowledge`, regardless of the source repositories' names or visibility. Verify `private: true` from GitHub before the first write and before publishing sensitive material. A branch or directory in a public repository is public. Only use shared or public knowledge deliberately after confirming disclosure scope. See [knowledge-standard.md](references/knowledge-standard.md).
4. **Use the provider's native planning and delivery.** Link an existing GitHub Projects V2 board to the Workspace project when selected; the board may track issues/PRs from multiple repositories. Reuse GitHub Issues, sub-issues, labels, milestones, Projects fields, Discussions, PR reviews, rulesets, Actions/checks, Releases and Packages/GHCR only where available and authorized. GitHub owns their mutable status; do not duplicate them in Markdown. See [github-workflow.md](references/github-workflow.md).
5. **Protect repository identity.** GitHub `owner/name` and URL are mutable locators. Record the provider's numeric repository `id` and current `full_name` when establishing a link. On a rename or transfer, verify the same `id` at the destination, run the controller's authorized `github_account_reconcile` (or its verified rename/transfer workflow), and re-read all project, library, knowledge and checkout references. If the change occurred outside Workspace, reconcile explicitly; **do not rely on GitHub URL redirects** or assume the controller noticed. Preserve immutable historical citations. See [project-model.md](references/project-model.md).
6. **Plan work at the right scope.** Use a repository Issue for repository-specific changes and a cross-repository GitHub Project for shared milestones; avoid duplicate issues. Cite cross-repo dependencies, commits and artifact IDs. Obtain appropriate review and respect checks, branch protection and provider-scoped permissions. Do not create accounts, boards, repositories or permission grants as an unrequested convenience.
7. **Implement and verify.** For source changes apply the independent `professional-code` skill, or its current principles if unavailable. Match repository conventions, repair root causes, maintain the root `REFERENCES.md`, run proportionate tests and review the diff. Distinguish passing source tests from a deployed integration and from completed runtime execution. Use [mcp-operations.md](references/mcp-operations.md) and [cluster-and-delivery.md](references/cluster-and-delivery.md) for compute, hardware, artifact, resource and recovery procedures.
8. **Publish to the correct authority.** Verify expected source/knowledge heads and provider identities; push through the selected Git tool, re-read the committed revision, and use native PR review/merging where applicable. Store large binary outputs as digest-verified artifacts or appropriately authorized packages, not silently in Git history. Release leased resources only after observing teardown.
9. **Persist only durable knowledge.** When `knowledge_policy=none`, do not save project notes or handoffs. When `git`, write under the approved knowledge repository and prefix using expected-head checks, then verify Git readback. Project knowledge is for decisions, reproducible findings, experimental records and concise state—not activity logs. Follow [knowledge-standard.md](references/knowledge-standard.md).
10. **Close with evidence.** Update GitHub Issues/Projects only after the relevant acceptance result is observed. Report actual source SHAs, linked items, artifacts and hashes, tested behavior, released resources and outstanding blockers. Do not assert the existence of a private repository, successful transfer or working native integration from a skill description alone.

## Clean project records

Write each file as though it were permanent technical documentation, not an account of an assistant's session. Never add self-referential completion notes (for example, “did not change X”), transient to-do transcripts, prompt dumps, duplicated status tables, bot bylines, generated-by-assistant statements, obsolete variant files or unnecessary assistant-specific configuration. Prefer a short, current-state `Context.md` and real evidence references. Preserve legitimate author attribution, required licenses, audit trails and truthful provenance; do not falsify authorship or erase required history. Apply the same discipline to issues, PR descriptions, commit messages, release notes, package metadata and project boards. Do not add a record solely to demonstrate that a request was followed.
