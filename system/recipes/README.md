# First-party recipes

The Go platform owns recipe, planned-meal and shopping data. The Dioxus browser UI is a client, not another recipe server. The recipe store persists to `HOMELAB_RECIPES_FILE` (default: a private `recipes.json` beside the platform's state file) using atomic file replacement and revision checks. Storage and HTTP handlers are independent of the RecipeSage compatibility adapter.

## Resources

- `GET /v1/recipes?query=...`, `POST /v1/recipes`, `GET/PUT/DELETE /v1/recipes/{id}`.
- `GET /v1/recipes/{id}/nutrition?servings=N` returns a sourced nutrient preview; absent values remain absent.
- `GET /v1/recipes/{id}/history`: list the current version followed by up to 20 earlier recipe snapshots. `POST /v1/recipes/{id}/restore` with `{"source_revision":N,"expected_revision":CURRENT}` restores a retained snapshot **as a new revision** and rejects stale current revisions. The same operations are available as `recipe_history` and `recipe_restore` MCP tools.
- `GET /v1/recipes/health-goals` reads the existing Health integration's nutrient and physiological targets where available. It does not alter Health records.
- `GET /v1/meals`, `POST /v1/meals`, `DELETE /v1/meals/{id}`.
- `GET /v1/groceries?start=YYYY-MM-DD&end=YYYY-MM-DD` consolidates scaled quantities by ingredient name and unit. It does not assume that differently named ingredients or different units are interchangeable.
- `GET /v1/groceries/needs?start=YYYY-MM-DD&end=YYYY-MM-DD` returns recorded stock, required quantities, remaining amounts to buy, and stock uncertainty for the same meal-plan date range. Only unexpired pantry quantities with the same normalized ingredient and unit are subtracted. This is an advisory view; grocery checklist marks do not consume or replenish stock. The `recipe_grocery_needs` MCP operation returns the same derived data.
- `GET /v1/pantry` returns the owner-owned pantry ledger and current revision. `PUT /v1/pantry` accepts `{"item":{"name":"Rice","unit":"g","amount":500,"expires":"2026-12-31"},"expected_revision":0}`; the expiry date is optional. `DELETE /v1/pantry/items/{key}` accepts `{"expected_revision":1}`. Only exact ingredient-unit keys match; zero stock is represented by removing the entry. Revisions prevent lost updates.
- `POST /v1/recipes/recommend` accepts `{"servings":1,"targets":[{"name":"protein","unit":"g","remaining":40}],"limit":20}`. It ranks recipes by recorded pantry coverage and known nutritional-target fit while identifying ingredient shortages and unknown nutrients. Targets are caller-supplied; this operation neither logs food nor changes Health or pantry records. Corresponding MCP tools are `recipe_pantry_list`, `recipe_pantry_set`, `recipe_pantry_remove`, and `recipe_recommend`.
- `GET /v1/recipes/export`, `POST /v1/recipes/import`: portable, versioned JSON (version 1) holding `recipes`, `meals`, `pantry`, and any retained recipe revision history.
- `GET /v1/recipes/bundle`, `POST /v1/recipes/bundle`: portable ZIP holding `recipes.json` plus each content-addressed `images/<sha256>.jpg` or `images/<sha256>.png` referenced by current recipes or retained history. ZIPs have a 96 MiB limit, up to 128 referenced photographs and a 16 MiB JSON manifest limit. The import validates ZIP filenames, decompressed image sizes, content hashes and image data; it rejects missing or unreferenced images and never replaces an existing recipe ID. The owner-session import requires `application/zip` and the CSRF token.
- `POST /v1/recipes/import-url` with `{"url":"https://..."}`: fetch a public HTTPS document, extract schema.org Recipe data and return an **unsaved draft** for human review. The same operation is available through the `recipe_import_url_preview` MCP tool.
- `POST /v1/recipes/recipesage/preview` with `{"source":"<RecipeSage JSON-LD export>"}`: inspect up to 1,000 recipes from an export file (8 MiB maximum), returning stable source keys, title, structured draft, eligibility, and warnings. This endpoint never writes records.
- `POST /v1/recipes/recipesage/import` with `{"source":"...","digest":"<preview digest>","keys":["recipesage:<sha256>",...],"overrides":{"recipesage:<sha256>":{<reviewed recipe>}}}`: import only explicitly selected valid entries. The server reparses the original export, rejects a stale digest, and commits the selected records atomically. Existing RecipeSage identities and repeated selections produce a conflict; neither similar titles nor partial imports cause replacement. Validated `overrides` allow owner-corrected ingredient quantities or other recipe fields while retaining the original import identity; unselected changes and fabricated record IDs are rejected. The operations are also exposed as `recipe_sage_preview` and `recipe_sage_import` MCP tools.
- `POST /v1/recipes/images` with a raw `image/jpeg` or `image/png` body: store an immutable image (5 MiB and 16 megapixel limits), then return `{"image_ref":"/v1/recipes/images/{sha256}.jpg"}` or the corresponding PNG reference. `GET /v1/recipes/images/{name}` retrieves that image using the same recipe read permissions. Uploaded images are available to attach to a recipe after an explicit save; uploading alone does not modify recipe records.

Recipe edits use the existing stored `revision` as an optimistic concurrency guard. Deletion requires an `If-Match` header containing the current revision and fails while a meal references the recipe. An import never overwrites existing IDs. Browser writes require a valid owner-session cookie, an approved Origin, the session's `X-CSRF-Token`, and the expected media type (JSON for record changes; JPEG or PNG for images). The privileged cluster executor and MCP bearer credentials are not involved.

## Data and integration boundaries

The legacy `/v1/groceries` response is a derived preview. The first-party `/v1/groceries/board` and `/v1/groceries/items/{key}` routes persist an owner-confirmed checked/purchased ledger with optimistic revision checks. Identical ingredient names with different units remain separate; checklist status is keyed by normalized ingredient/unit, not by individual shopping trip. Image files reside in a private `images/` directory next to the recipe database. JPEG and PNG payloads are decoded before storage, use SHA-256 filenames to deduplicate identical content, and are never retrieved from a remote image URL. JSON exports contain image references but no binary media. To transfer photographs together with records, use the portable ZIP endpoint. Image files remain immutable in private storage; failed ZIP imports may leave unreferenced images that can be reused when the archive is imported successfully. Orphaned uploads are not automatically removed, and no image transformations or metadata stripping are performed. Schema.org JSON-LD recipe drafts can be extracted from pasted markup or one public HTTPS page. URL imports require public DNS answers, pin resolved addresses for the TLS request, disable proxies and redirects, and limit the response to 512 KiB over 10 seconds. A fetched draft requires explicit owner review and saving; scripts, linked assets and images are not fetched. Sites that block automated requests, redirect, or omit schema.org Recipe markup cannot be imported this way. RecipeSage JSON-LD import copies supported ingredients, instructions, servings, times, labels, notes, source credits, source URL, and explicitly reported standard nutrients. Missing quantities mark a candidate for review. The owner may correct the editable recipe in the Rust console and include those corrections in the same validated import; unknown nutrition units are not guessed. External images, linked-recipe relationships, historical ratings, original ingredient formatting and unsupported nutrient text are not converted to first-party structured fields. Relevant details are retained as notes where possible; the preview warns about omitted media and incompatible fields. The original RecipeSage export and installation remain the source for any data requiring manual review. PDF and image extraction, micronutrient inference and automatic Health meal-plan synchronization remain unimplemented. A first-party recipe with existing nutrition may be submitted as an explicitly unconfirmed Health meal proposal. Health only records consumption after separate owner confirmation. Until migration is explicitly approved, RecipeSage remains available and its data untouched. Do not import or remove its data based on an assumption that the original database is empty.
